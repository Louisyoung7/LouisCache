# LouisCache 缓存策略压测说明

本目录是 LouisCache 各缓存策略（`Lru` / `LruK` / `ShardedLru` / `Lfu` / `ShardedLfu` / `Arc`）的 Google Benchmark 压测程序。

这份文档回答四个问题：**测什么、为什么这么测、测出了什么、怎么跑**。

---

## 1. 目的与范围

压测的目标不是"测出一个最快的策略"，而是回答一个决策问题：

> 在什么流量形态下，哪个策略更划算，代价具体付在哪里？

因此本项目做两类工作：**已有缓存策略的性能对比**（三层计时压测）与**命中率研究**（容量扫描，见 §2.4 / §4.8）。明确不做：

- 语义缓存 / Embedder / VectorIndex
- 内存占用统计、自动出图
- "策略 × 容量 × 分布 × 线程"的全矩阵（命中率研究固定单线程，多线程不参与容量扫描）

---

## 2. 测试方式

压测分三层计时基准 + 一个不计时的研究工具，各自回答不同的问题，**绝对值不能跨层比较**。

### 2.1 第一层：单操作微基准（[bench_ops.cc](bench_ops.cc)）

把每个操作拆开单独测，回答"某条代码路径本身有多贵"。

| 场景 | 含义 |
|---|---|
| `GetHit` | 命中已有 key |
| `GetMiss` | 查询不存在的 key |
| `PutOverwrite` | 覆盖已有 key |
| `PutNew` | 插入新 key（满容量后伴随淘汰） |
| `Remove` | 删除已有 key |
| `Exists` | peek 语义的存在性查询 |

实现要点：

- 被测对象是 `louis::cache::Policy<Key, Value>` 虚接口，容量统一 1024，`Key = Value = uint64_t`。
- 当前策略通过 `registerForPolicy` 注册成 `策略名/操作名`，共 6 × 6 = 36 个基准。
- 构造与预热放在 Google Benchmark 的 `Setup` / `Teardown` 回调里，**不计入计时**。
- 热工作集 `kWorkingSet = kCapacity / 2 = 512`，避免 ARC 初始 `T1` 目标容量（`capacity/2`）导致一半 key 进幽灵缓存。
- `Remove` 场景删完后需要恢复数据，恢复用 `PauseTiming` / `ResumeTiming`，且**必须放在 range-for 循环内**（放循环外会把整段计时污染成毫秒级）。
- 输出 `hits_per_iter` / `found_per_iter` 计数，用于确认真的走在了预期路径上，而不是测了个空循环。

### 2.2 第二层：流量回放（[bench_workloads.cc](bench_workloads.cc)）

用一段预生成的 key 序列模拟真实请求，回答"整体表现如何"。

- trace 由 [trace.h](trace.h) 生成：固定种子、固定长度 4096、key 空间 = 4 × 容量（4096）。
- 六种分布：

| 分布 | 构造方式 | 用来暴露什么 |
|---|---|---|
| `Uniform` | 在 `[0, 4096)` 内等概率抽取 | 最坏情况压力 |
| `Sequential` | 0 → 4095 递增回绕 | 顺序扫描病态 |
| `Zipf` | 第 r 名概率 ∝ 1/r^s（s = 1.0），逆 CDF 采样 | 真实热点负载近似 |
| `ScanMix` | 每 100 次 = 90 次热点（key 0..1023）+ 10 次连续冷扫描（key 4096..8191） | 扫描污染：热点是否被一次性冷数据挤出 |
| `LongScan` | 5 个周期，每周期 = 2048 次热点 + 1024 次连续冷扫描 | 整表扫描：容量被整体冲掉后能否恢复 |
| `PhaseShift` | 2 个周期，每周期 = 2048 次 Zipf（key 0..1023）+ 2048 次均匀（key 1024..2047） | 访问模式漂移：频率型与最近型来回切换 |

回放语义：

1. **预填充** `0..1023`（与 trace 分布无关），让所有策略从"刚写满容量"的同一状态出发。
2. 逐 key 执行 `get`；命中则结束。
3. 未命中则 `put` 回填——写满容量后**淘汰自然发生**。
4. 通过 `LeaveReason::Evicted` 的回调统计淘汰次数（`Explicit` 不计）。
5. 每个迭代都重建 cache 并重新预填充，保证每轮从相同初始状态开始。
6. 输出 `hits_per_iter` / `misses_per_iter` / `evictions_per_iter` / `cache_size` / `hit_rate_pct`，并用 `SetItemsProcessed` 输出 items/s。

### 2.3 第三层：多线程并发回放（[bench_threads.cc](bench_threads.cc)）

把同一条 trace 分给 n 个线程同时回放，共享同一个缓存实例，回答"锁结构能不能伸缩"。

- 对比两个算法家族：`Lru` / `Lfu`（整个缓存一把锁，基线）与 `ShardedLru` / `ShardedLfu`（按 key 哈希分片、每片一把锁），分片数取 **1 / 2 / 4 / 8 / 16**，负载取 `Zipf` 与 `Uniform`，线程数取 1 / 2 / 4 / 8。S1 用于验证"分片机制本身的额外开销"，S4 是产品默认值，S16 超过最大线程数，用于观察锁数量多于线程数时是否仍有收益。两个家族对比的目的是验证**分片伸缩性是分片实现的性质，与缓存算法无关**。基准名形如 `ShardedLru-S4/Threads-Zipf`，片数直接写在名字里。
- **每线程一条独立种子的同分布 trace**（`kTraceSeed + 1000 * t`）。若所有线程复读同一条序列，它们会在同一时刻访问同一个 key，这种人伪同步会放大锁争用。
- 线程池在 `Setup` 中一次性创建并常驻，每轮只做"唤醒 → 跑 → 汇总"。每轮新建 `std::thread` 会让 CPU 从低频态爬起来，单线程实测被放大到 5 倍；忙等自旋也会与主线程抢核，改用 `std::mutex` + 两个 `condition_variable`。
- **`threads = 1` 时不创建线程池**，直接在主线程跑。实测哪怕只留一个空闲 worker，主线程耗时也会翻倍——单线程基线必须与 `bench_workloads` 的口径对齐才可比。
- 单次迭代固定约 20 万次访问（`kTargetItemsPerIter`），由 `repeats` 把条件变量唤醒开销（几十 µs）摊薄到 0.1% 量级。
- **稳态口径**：缓存在 `Setup` 里只预热一次，之后所有迭代都跑在同一个热缓存上，不做每轮冷启动重置。因此本层测的是持续并发吞吐，**绝对值不可与 §4.2–§4.5 的冷启动回放横比**。
- 同时输出自测墙钟（`ns_per_item` / `items_per_sec`）与工人内部自测（`busy_ns_per_item`）。`busy_ns_per_item` 是各工人执行时长之和按总条目摊平，正常约为 `ns_per_item × 线程数`，说明所有工人全程都在跑；某线程明显偏短则说明哈希分片不均导致负载倾斜。它是**并行度校验**，不是"同步开销 = 两者之差"。

### 2.4 命中率研究：容量扫描（[hitrate_study.cc](hitrate_study.cc)，不计时）

计时基准已经证明各策略速度在同一量级，策略之间真正拉开差距的是命中率——而命中率的主变量是**容量比例**（capacity / 访问域大小）。第二层只在 `capacity = 1024` 一个点上抽查命中率，本工具把这一个点展开成整条曲线。

- **不计 时、只统计**：命中率与耗时无关，跑一遍计数即可，套 benchmark 的 min_time / repetitions 框架纯属浪费。全量 6 分布 × 7 容量档 × 6 策略 × 2 遍回放约 5 亿次访问，单线程 7 秒跑完。
- **唯一变量是容量**：trace 完全固定（与 §2.2 同一批生成器、固定种子，但拉长到约 10 万条以保证小容量档的样本量），capacity 从访问域 4096 的 1/64 扫到 1/1 共 7 档。
- **稳态口径**：同一策略实例上回放两遍，第一遍预热不计数，第二遍为稳态命中率。第二层（§4.2–§4.5）是冷启动口径，两者数字不可横比。
- **回放语义与第二层一致**：get 命中即止，miss 则 put 回填。
- 输出每分布一张表（行 = 容量档，列 = 策略），并写一份长表 CSV（`distribution,policy,capacity,hit_rate_pct`）供以后画图；路径由第一个命令行参数指定。

## 3. 为什么这么测

每一条设计都对应一个"不这么做会得到错误结论"的具体风险。

| 设计 | 不这么做会怎样 |
|---|---|
| 同一份预生成 trace | 每个策略用不同随机序列，差异分不清是策略不同还是运气 |
| 固定随机种子 | 结果不可复现，"同策略重复跑计数一致"这条验收无从谈起 |
| 预填充到容量 | 各策略起点不同（有人空、有人满），命中率不可比 |
| 每迭代重置 cache | 第二遍开始变成热缓存，命中率接近 100%，测的不是冷启动负载 |
| 未命中时 put 回填 | 只有 get 的话永远不会淘汰，`evictions` 恒为 0 |
| 同时输出命中/未命中/淘汰计数 | 只看 ops/s 会把"命中率高但单次慢"和"单次快但一直 miss"混为一谈 |
| 热工作集取容量一半 | ARC 初始 T1 目标为容量一半，写满 1024 会有 512 个进幽灵缓存，`GetHit` 会混入未命中 |
| 所有策略走 `Policy&` 虚接口 | 直接用具体类会少约 11 ns/op，且各策略优化差异不可控 |

**两种测试不能混比**：`bench_ops` 的 `GetHit` 只测命中路径；`bench_workloads` 的单项耗时混了命中、未命中、回填、淘汰。里程碑 1 的 25 ns 与里程碑 3 的 52 ns 不是退化，是口径不同。

## 4. 测试结果

环境：32 核 5400 MHz，L1d 48 KiB、L2 2 MiB、L3 36 MiB，Release 构建，`benchmark_min_time=0.3s`，3 次重复取中位数。存在 `CPU scaling is enabled` 警告，绝对值会随系统负载波动（两轮实测差异约 3–5%），优先看相对倍率。

|---|---:|---:|---:|---:|---:|---:|
| Lru | 37.5 | 7.3 | 39.6 | 69.6 | 40.6 | 6.2 |
| LruK | 41.4 | 19.2 | 49.8 | 90.4 | 71.3 | 11.3 |
| ShardedLru | 38.8 | 9.2 | 42.6 | 73.0 | 45.5 | 6.5 |
| Lfu | 61.3 | 7.0 | 61.8 | 89.1 | 46.8 | 7.0 |
| ShardedLfu | 64.7 | 9.1 | 64.9 | 93.4 | 54.6 | 7.4 |
| Arc | 378 | 13.2 | 345 | 155 | 56.4 | 6.8 |

### 4.2 流量回放（第二层，4 × 容量，4096 次访问）

|---|---:|---:|---:|---:|---:|

| Lfu | 76.7% | 79.9 | 12.52 M/s | 23.9% | 25.0% |
| ShardedLfu | 76.8% | 101.0 | 9.90 M/s | 24.0% | 25.0% |

|---|---:|---:|---:|---:|

### 4.3 扫描混合回放（ScanMix）

热点集合取满容量 1024，每 100 次访问中插入 10 次连续冷扫描——这是唯一能暴露"抗扫描污染"能力的负载。

| 策略 | 命中率 | hits | misses | evictions | 单次 ns | 吞吐 |
|---|---:|---:|---:|---:|---:|---:|
| Lru | 77.1% | 3160 | 936 | 936 | 51.1 | 19.56 M/s |
| LruK | 65.7% | 2692 | 1404 | 0 | 78.2 | 12.78 M/s |
| ShardedLru | 77.1% | 3156 | 940 | 940 | 59.9 | 16.69 M/s |
| **Lfu** | **81.0%** | **3319** | **777** | 777 | 71.3 | 14.02 M/s |
| **ShardedLfu** | **81.1%** | **3321** | **775** | 775 | 80.6 | 12.41 M/s |
| Arc | 58.8% | 2410 | 1686 | 1176 | 189.7 | 5.27 M/s |

结论：

- **只有 Lfu / ShardedLfu 相对 Lru 有可测量的优势**：命中率高 3.9 个百分点，因为扫描 key 的频次恒为 1，会被优先淘汰，热点频次高所以留得住。代价是单次更贵（71.3 vs 51.1 ns），吞吐反而低。
- **LruK 反而更差**：它的 k=2 晋升要求让每个热点 key 首次访问必 miss（约 1024 次），仅这一项开销就超过了扫描保护带来的收益。本轮扫描突发只有 10 个 key，远小于容量，污染强度不足以体现 LruK 的价值（整表扫描场景见 4.4）。

### 4.4 整表扫描回放（LongScan）

每周期 2048 次热点 + 1024 次连续冷扫描，扫描长度正好等于容量，能把 LRU 的缓存整体冲掉；跑 5 个周期，第 1 个作预热。

| 策略 | 命中率 | hits | misses | evictions | 单次 ns | 吞吐 |
|---|---:|---:|---:|---:|---:|---:|
| Lru | 43.6% | 6691 | 8669 | 8669 | 65.6 | 15.24 M/s |
| **LruK** | **58.8%** | **9037** | **6323** | 0 | 73.2 | 13.66 M/s |
| ShardedLru | 43.6% | 6691 | 8669 | 8669 | 74.2 | 13.48 M/s |
| **Lfu** | **65.5%** | **10057** | **5303** | 5303 | 71.9 | 13.90 M/s |
| **ShardedLfu** | **65.5%** | **10057** | **5303** | 5303 | 79.0 | 12.66 M/s |
| Arc | 49.0% | 7529 | 7831 | 7333 | 208.2 | 4.80 M/s |

结论：

- **LruK 的优势成立**：58.8% vs Lru 43.6%，高 15.3 个百分点。原因是扫描 key 只被访问一次，进不了主缓存；热点 key 早已晋升，扫描冲不掉它们。代价是单次慢 12%（73.2 vs 65.6 ns）。
- **Lfu 依然最好**：65.5%，且没有 k=2 的首次 miss 成本。LruK 与 Lfu 的排序在"扫描污染"场景下稳定为 Lfu > LruK > Lru。
- **Arc 介于两者之间**（49.0%），但单次是 Lru 的 3.2 倍，性价比最差。
- **LruK 的 `evictions` 仍为 0**：热点集合恰好等于容量 1024，主缓存被热点填满后扫描 key 一个都升不进来，所以主缓存从不淘汰——这正是它想要的效果。
- **Arc 的 evictions(7333) 小于 misses(7831)**：进入幽灵缓存的未命中不计为淘汰，属于统计口径差异。

### 4.5 相位切换回放（PhaseShift）

每段 2048 次访问在"频率型（Zipf over 0..1023）"与"最近型（均匀 over 1024..2047）"之间交替，用来检验 ARC 的幽灵队列反馈能否适应负载漂移，以及 LFU 是否会被陈旧频次拖累。

| 策略 | 命中率 | hits | misses | evictions | 单次 ns | 吞吐 |
|---|---:|---:|---:|---:|---:|---:|
| **Lru** | **74.6%** | **6111** | **2081** | 2081 | **54.2** | **18.45 M/s** |
| LruK | 61.6% | 5043 | 3149 | 774 | 91.0 | 11.00 M/s |
| ShardedLru | 74.6% | 6114 | 2078 | 2078 | 61.3 | 16.31 M/s |
| Lfu | 69.9% | 5730 | 2462 | 2462 | 84.2 | 11.87 M/s |
| ShardedLfu | 69.9% | 5724 | 2468 | 2468 | 101.7 | 9.84 M/s |
| Arc | 69.4% | 5684 | 2508 | 2006 | 198.3 | 5.04 M/s |

结论：

- **Lru 反而最适合相位切换**：74.6%，因为它"忘得最快"——相位一切换就能立刻淘汰旧集合、拥抱新集合。
- **LFU 被陈旧频次拖累**：69.9%，比 Lru 低 4.7 个点。相位 A 的高频记录在相位 B 里仍然压着新 key，这正是频次型策略的经典弱点。
- **ARC 没有把适应性兑现**：69.4%，与 LFU 基本持平，但单次是 Lru 的 3.7 倍。幽灵队列的反馈确实存在，但在 2048 次的相位长度内还不足以调准 `p`。
- **LruK 最差（61.6%）**：k=2 的首次 miss 成本 + 相位切换时历史队列被反复冲刷。

### 4.6 淘汰计数器验证（A/B：`kUniverse` 4× → 2×）

目的：确认 LruK 的 `evictions = 0` 到底是"没发生淘汰"还是"计数器没接通"。只跑 LruK：

| 配置 / 分布 | 命中率 | hits | misses | evictions | cache_size |
|---|---:|---:|---:|---:|---:|
| 4× / Zipf（基线） | 68.4% | 2802 | 1294 | 0 | **732** |
| 2× / Zipf | 75.0% | 3073 | 1023 | 0 | **731** |
| 2× / Uniform | 36.1% | 1479 | 2617 | **511** | 1024 |
| 2× / Sequential | 25.0% | 1024 | 3072 | **1024** | 1024 |

结论：`cache_size` 达到 1024 时 `evictions` 才非 0，说明计数器是好的，之前的 0 是真实"主缓存没写满"。同时纠正一个直觉：**收窄 key 空间不等于更多晋升**——Zipf 偏斜让访问集中在少数 key 上，2× Zipf 只有 731 个 key 达到晋升条件，反而更少。决定 LruK 是否淘汰的是"被访问 ≥ k 次的 distinct key 数 > 容量"，不是访问域大小。

### 4.7 多线程分片对比（两个家族 × 1 / 2 / 4 / 8 / 16 把锁）

稳态热缓存口径。`Lru` 与 `Lfu` 两个算法家族各带一套"全局锁基线 + 分片组"，用于验证**分片伸缩性是分片实现的性质，与缓存算法无关**。四个线程组在同一会话内分进程采集（每个线程数单独一个进程），3 次重复取中位数，`benchmark_min_time=0.5s`。单元格格式为 **ns/item（吞吐 M/s）**。

**Lru 家族，Zipf 负载**：

| threads | Lru（全局锁） | S1 | S2 | S4（默认） | S8 | S16 |
|---|---:|---:|---:|---:|---:|---:|
| 1 | 71.7（13.94） | 79.8（12.53） | 74.1（13.50） | 86.6（11.55） | 68.7（14.55） | 72.6（13.77） |
| 2 | 582.1（1.72） | 468.1（2.14） | 416.9（2.40） | 333.3（3.00） | 261.6（3.82） | 217.0（4.61） |
| 4 | 784.4（1.27） | 826.3（1.21） | 534.1（1.87） | 365.4（2.74） | 293.3（3.41） | 191.1（5.23） |

- **命中率列只作诊断**：Lfu 家族 Zipf 稳态 84–86%（Lru 家 77–78%），与 §4.8 一致。Uniform t1 高达 39%（Lru 恒 24%）是回放方式的人造信号——同一条 4096 key 的 trace 重复回放 48 遍，LFU 的频次结构会锁住这条 trace 的经验热点；线程数越多，不同种子的 trace 交错，信号越稀释（t8 降到 29–30%）。命中率绝对值以 §4.8 的长 trace 研究为准。
- **t8 档绝对值跨会话可漂移 30–40%**：Lru t8 Zipf 两轮采集分别为 731 / 1029 ns（powersave governor 频率态不同）。**看同会话内的相对排序与倍率，不要跨会话比绝对值。**
- **同步开销仍可忽略**：`busy_ns_per_item` 约为 `ns_per_item × 线程数`，8 个工人整轮都在执行，条件变量握手没有把某个线程挂在等待上。

## 5. 结论与局限

### 5.1 能站住脚的结论

1. **没有全能最优**。Zipf 下 Lru 命中率最高且单 op 最快；Arc 命中率只差约 5 个点，单次却慢 3 倍。
2. **LruK 的成本与收益都测到了**：Zipf 下因 k=2 首次必 miss，命中率比 Lru 低约 8 个点；整表扫描（LongScan）下反超 15.3 个点（58.8% vs 43.6%）。它的价值只在"扫描污染"场景成立。
3. **分片是"单线程几乎不付成本、多线程按锁数量线性赚回来"，且与缓存算法无关**：8 线程下吞吐随分片数单调上升，S16 相对全局锁 **Lru 家 5.8×（Zipf）/ 7.3×（Uniform）**、**Lfu 家 3.5× / 6.9×**。默认的 4 片并不是最优，只是成本与粒度的折中。但 LFU 家族的收益打折（单操作更贵），且其单线程分片在 Zipf 下单调变慢（S16 比 Lfu 慢 1.9×），与 Lru 家族相反。
4. **Lfu 的命中路径明显更贵**（61.3 vs 37.5 ns），因为每次命中要更新频次结构；但它的 miss 路径最便宜（7.0 ns）。
5. **Arc 有明确的顺序扫描病态**：Sequential 命中率 0%，扫描插入时淘汰的恰好是即将访问的旧 key。这是算法特性，不是缺陷。
6. **扫描污染下 Lfu 与 LruK 都能胜过 Lru**：LongScan 命中率 Lfu 65.5% > LruK 58.8% > Lru 43.6%；但两者吞吐都低于 Lru（13.90 / 13.66 vs 15.24 M/s），都是用速度换命中率。ScanMix（污染较弱）下只有 Lfu 领先（81.0% vs 77.1%），LruK 则因首次 miss 成本而落后。
7. **Arc 的收益几乎无法兑现，且多一笔结构性代价**：冷启动口径下（§4.2–§4.5）它在全部负载被至少一个更简单的策略同时压制；稳态容量扫描（§4.8）里也仅在 PhaseShift 25% 档拿到唯一一次全场最佳（79.08% vs Lfu 76.15%），其余档位仍被压制。此外它在"容量 = 访问域"的循环扫描下只有 34.57%（理论 100%），分侧硬上限 + 幽灵反馈造成自持抖动。以当前证据，**它的实现复杂度换不来可测量的净收益**；理论价值是"未知负载下的保险"，而本轮所有负载都是已知的。
8. **容量比例是命中率的第一变量，排名随它翻转**：Zipf 下小容量（≤12.5%）LruK/Lfu/Arc 领先 Lru 约 11 点，大容量（≥50%）收窄到 3 点以内；PhaseShift 下小容量 Lru 最好、25% 档换 Arc。任何"策略 A 命中率更高"的说法都必须带上容量比例才成立。
9. **口径不同，结论可以翻转**：ScanMix 下 LruK 在冷启动短 trace（§4.3）落后 Lru 11.4 点，在稳态长 trace（§4.8）反超 16.9 点——k=2 的首次 miss 成本被 10 万条 trace 摊薄后，扫描保护收益才显现。评估策略必须先声明口径。

### 5.2 不能下的结论（必须写清楚）

- **绝对值不可外推**：单线程、容量 1024、`uint64_t` 值、trace 长度 4096–15360；换机器、换规模都会变。
- **存在约 11 ns 的虚接口成本**：所有策略都走 `Policy&`，可横向比较，但不可与里程碑 1 的绝对值比较。
- **命中率有两套口径**：§4.2–§4.5 是冷启动口径（每轮从"预填充 1024 个 key"开始）；§4.8 是稳态口径（预热一遍数第二遍）。两套数字不可横比，引用时必须带上口径。
- **Arc 满容量抖动的机制是源码推断**：34.57% 的解释来自阅读 `applyPartitions` 的 p 钳制与分侧硬上限，没有做逐条 trace 验证。
- **LongScan 4096 档 LruK 反超 Lfu 的机制未深究**：只有数据（86.81% vs 75.76%），没有验证"历史队列让被冲掉的热点快速重进"的猜想。
- **命中率研究是单线程口径**：没有验证并发下的命中率行为；ScanMix / LongScan / PhaseShift 的热点集与扫描跨度沿用按容量 1024 设计的常量，容量扫到 2048 / 4096 档时热点集已小于容量，那几档更接近"容量上限实验"而非污染实验。
- **LruK 淘汰只统计主缓存**：`LruKCache` 只给 `mainCache_` 注册了 leave 回调，历史队列的淘汰未计入。
- **LruK 的收益有场景与口径限制**：冷启动口径下只在整表扫描（`LongScan`）成立；稳态长 trace 下 `ScanMix` 与小容量 `Zipf` 也成立（§4.8）。但 25% 以上容量的 Zipf / Uniform 中，k=2 的首次 miss 成本仍是净亏损或仅剩零点几个点。别把扫描场景的结论套到无扫描的负载上。
- **噪声**：CPU scaling 开启，`Remove` 场景 CV 约 2.8%，来自 `PauseTiming` 恢复数据的分配器波动。
- **多线程是稳态热缓存口径**：§4.7 的缓存只在 `Setup` 预热一次，绝对值不可与 §4.2–§4.5 的冷启动回放横比；它回答的是"持续并发吞吐"，不回答"冷启动首次命中率"。
- **多线程基准须分进程采集**：powersave governor（i9-13980HX，频率在 800 MHz–4.7 GHz 间跳变）下同进程内跨基准切换会造成 2 倍级波动，故每个 threads 值单独起一个进程，必要时配合 `taskset -c` 绑核。
- **多线程验证了两个家族的锁结构，没有覆盖全部策略**：已测 `Lru` / `ShardedLru` / `Lfu` / `ShardedLfu`；`LruK` / `Arc` 的并发伸缩性未知。
- **LFU 家族单线程分片变慢的机制未深究**（§4.7）：Zipf 下 S16 比 Lfu 慢 1.9× 且随片数单调，推测与每片频次结构的局部性有关，没有做 profile 验证。
- **LFU 多线程命中率含人造频次信号**：有限长度 trace 被重复回放，LFU 会锁住经验热点（Uniform t1 达 39%），不能当作稳态命中率引用（§4.7）。
- **分片数只测到 16**：S16 在 8 线程下仍有收益，继续加到 32 / 64 是否还能涨没有数据；同时每片容量 = 1024 / 片数，片数过大（如 128 片 → 每片 8 槽）必然开始损失命中率，本轮未触及这个拐点。
- **分片带来的"单线程局部性收益"来源未深究**：Lru 家族 S8/S16 单线程反而略快，推测是每片哈希表更小，但没有做 profile 验证。
- **多线程的相对倍率仍受硬件影响**：线程数超过物理核数或与超线程共享时，竞争形态会变，4.6–7.3 倍不能直接套到其他机器。

产物：`build/Release/bin/benchs` 与 `build/Release/bin/hitrate_study`。

依赖：`conanfile.py` 中的 `benchmark/1.9.5`；根 `CMakeLists.txt` 中通过 `BUILD_BENCHMARKS` 开关控制是否编译压测。

### 6.2 运行

```bash
# 全量（36 个单操作 + 36 个回放 + 96 个多线程）
./build/Release/bin/benchs

# 只跑流量回放
./build/Release/bin/benchs --benchmark_filter='Replay'

# 只跑多线程分片对比
./build/Release/bin/benchs --benchmark_filter='Threads-'

# 只跑某个分片数（S1 / S2 / S4 / S8 / S16）
./build/Release/bin/benchs --benchmark_filter='ShardedLru-S8/'

# 只跑某个策略
./build/Release/bin/benchs --benchmark_filter='Lru/'

# 精确到某个基准
./build/Release/bin/benchs --benchmark_filter='LruK/Replay-Zipf'

# 多线程基准推荐：每个线程数单独一个进程，避免跨基准的频率态互相污染
for t in 1 2 4 8; do
  ./build/Release/bin/benchs \
    --benchmark_filter="/threads:$t/" \
    --benchmark_min_time=0.5s \
    --benchmark_repetitions=3 \
    --benchmark_report_aggregates_only=true
done

# 只跑某类操作
./build/Release/bin/benchs --benchmark_filter='GetHit'

# 列出全部基准名（不执行）
./build/Release/bin/benchs --benchmark_list_tests

# 推荐：多轮重复 + 只输出聚合值
./build/Release/bin/benchs \
  --benchmark_min_time=0.3s \
  --benchmark_repetitions=3 \
  --benchmark_report_aggregates_only=true

# 输出 JSON 存档
./build/Release/bin/benchs --benchmark_format=json --benchmark_out=build/bench.json

# 命中率研究：不计时、单线程、约 7 秒跑完全部 6 分布 × 7 容量档 × 6 策略
# CSV 路径由第一个参数指定，默认 hitrate_results.csv（写在当前目录）
./build/Release/bin/hitrate_study
./build/Release/bin/hitrate_study build/hitrate_results.csv
```

### 6.3 常用参数

| 参数 | 作用 |
|---|---|
| `--benchmark_filter=<regex>` | 按名字筛选基准，支持前缀/子串匹配 |
| `--benchmark_min_time=0.3s` | 每个基准最少运行时间，时间越长越稳 |
| `--benchmark_repetitions=3` | 重复次数，用于算 mean / median / stddev / cv |
| `--benchmark_report_aggregates_only=true` | 只打印聚合值，输出更干净 |
| `--benchmark_list_tests` | 只列名字 |
| `--benchmark_format=json` | 机器可读输出 |

### 6.4 输出怎么读

- `Time`：每次迭代耗时。回放基准一次迭代 = 完整跑一遍 4096 条 trace。
- 单次耗时 = `Time / trace.size()`（回放）或 `Time / kWorkingSet`（单操作）。
- `items_per_second` = 每秒处理的 trace 条目数。
- `hit_rate_pct`：本轮命中率百分比。
- `cache_size`：回放结束时驻留条目数。**它和 `evictions` 要一起看**：`cache_size` 没到容量，就不该有淘汰。
- `iterations` 很小（如 3）且开了 repetitions 时，看 `_median` 而不是 `_mean`。
- **多线程基准的额外列**：
  - `slices`：分片数。`0` 表示单把全局锁（Lru），用于确认分片参数真的生效。
  - `ns_per_item`：每个线程每处理一个 key（get，未命中时再 put）的墙钟耗时，**含锁等待与同步开销**。
  - `busy_ns_per_item`：各工人执行时长之和 / 总条目，约等于 `ns_per_item × 线程数`。用于校验并行度与负载倾斜，不是"同步开销"。单线程档为 0（没有工人线程）。
  - `repeats`：每次迭代每个线程连跑几遍 trace。`iterations × threads × trace_size × repeats` 才是一次基准的总访问量。
  - `items_per_sec`：自测吞吐（总访问量 / 墙钟）。与 Google 的 `items_per_second` 应基本一致，可作为交叉校验。

## 7. 如何扩展

| 想做的事 | 改哪里 |
|---|---|
| 加一种访问分布 | 在 [trace.h](trace.h) 增加 `makeXxxTrace`，并在 `makeTraces()` 注册 |
| 调整 Zipf 偏斜度 | `kZipfExponent`（默认 1.0，越大越集中） |
| 改变 key 空间大小 | `kUniverse`（默认 `4 * kCapacity`） |
| 加长单次回放 | `kTraceSize`（默认 4096） |
| 加一个新策略 | 在 [policies.h](policies.h) 的 `makePolicy` 与 `kPolicyNames` 中登记，压测会自动注册 |
| 调整容量 / 分片数 | `policies.h` 的 `kCapacity` / `kSliceNum` |
| 改多线程测的线程数 | `bench_threads.cc` 的 `->Arg(...)` 链，以及 `kMaxThreads` |
| 改多线程测的分片数 | `bench_threads.cc` 的 `kSliceSizes` 数组 |
| 改命中率研究的容量档 | `hitrate_study.cc` 的 `kStudyCapacities` 数组 |
| 改命中率研究的 trace 长度 | `hitrate_study.cc` 的 `kStudyTraceSize` / `kStudyScanCycles` / `kStudyPhaseCycles` |
| 调多线程单次迭代的总访问量 | `bench_threads.cc` 的 `kTargetItemsPerIter` |
| 给多线程换一种负载 | `bench_threads.cc` 里 `RegisterAll` 增加一行 `registerThreads(...)` |
| 换值类型（如 `std::string`） | 修改 `policies.h` 的 `Value` 别名 |

增删 `benchmarks/*.cc` 之后必须重新执行 `cmake -S . -B build/Release`，否则 `file(GLOB)` 不会发现新文件。
