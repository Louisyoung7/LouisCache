本文面向两类问题：**HashEmbedder 为什么这么写**（实现），以及**它背后用到哪些算法与为什么成立**（原理）。全篇不需要 AI 背景；涉及 embedding 的通用概念时回链 [概念入门](../design/00-primer.md)。

## 一、它是什么，为什么存在

`HashEmbedder` 是 [Embedder 接口](../../src/Semantic/Embedder.h) 的一个**测试替身**：它把文本转成固定长度的浮点向量，但**不代表任何语义质量**。

它存在的理由写在 [关键设计决策 §4.7 零依赖原则](../design/03-design-decisions.md) 与 [贯穿性原则 5](../design/05-principles.md) 里：真实模型（ONNX Runtime / llama.cpp）是重依赖，一旦引入，单测就需要模型文件、算力甚至网络。而语义缓存真正复杂、最容易出错的部分是**编排逻辑**（精确命中先于 embedding、容量淘汰后的清理、TTL 过期、无幽灵命中）。用一个**确定、可复现、零依赖**的假 embedder，就能让这些逻辑在任意环境下被完整测通。

真实的语义质量是**可替换件**，阶段 2 才接入（[概念入门 §5](../design/00-primer.md)、[分卷 04 阶段 2](../design/04-roadmap.md)）。

它必须满足的契约就是 [Embedder](../../src/Semantic/Embedder.h) 的三个纯虚函数：

| 接口 | 语义 | 对 HashEmbedder 的约束 |
|---|---|---|
| `embed(text)` | 文本 → 向量 | 确定性：同输入必得逐字节相同的输出；且**相似文本的余弦相似度应高于无关文本** |
| `dim()` | 向量维度 | 固定且自洽，`embed()` 返回的长度必须等于它 |
| `modelId()` | 向量空间指纹 | 把影响向量空间的所有参数编进来，供持久化索引加载时校验（[概念入门 §6](../design/00-primer.md)） |

其中第二条的"相似文本应更相似"**不是**语义质量要求，而是**序关系**要求——只有它成立，"语义命中路径"这类用例才有断言对象。这是本实现里唯一需要算法支撑的地方，也是下文 §三 的全部动机。

## 二、总览：从文本到单位向量

整个 `embed()` 是一条确定性流水线，共六步：

```
输入文本
  │  ① 取字节视图      reinterpret_cast<const unsigned char*>
  ▼
字节序列
  │  ② 滑动 n-gram     每 n 字节一个窗口（默认 n=2），不足 n 时整串当一个窗口
  ▼
n-gram 序列
  │  ③ FNV-1a 哈希     每个窗口 → 64 位哈希（初值 = 偏移基数）
  ▼
64 位哈希值
  │  ④ MurmurHash3 终结器（mix）  位白化，打散低位相关性
  ▼
白化后的哈希
  │  ⑤ 定桶 + 定符号    桶 = h % dim（低位）；符号 = h 最高位 ? -1 : +1
  ▼
dim 维稀疏累加向量（±1 累加）
  │  ⑥ L2 归一化 + 零向量兜底
  ▼
单位向量（‖v‖ = 1）
```

每一层都只为解决上一层留下的一个具体问题，§三 逐条展开。

## 三、底层算法原理

### 3.1 为什么不用 `std::hash`

`std::hash<std::string>` 是**实现定义**的：C++ 标准不规定其算法，只要求"同一进程内一致"。实践中 libstdc++ 用 MurmurHash，libc++ 用 CityHash，且版本间会变。这直接违反本类的两条硬需求：

- **可复现**：跨进程、跨编译器的单测要得到同一向量；
- **持久化**：阶段 2 会把向量索引入库，重新加载时若哈希口径变了，老向量与新查询就落在不同空间，相似度全废。

所以必须自带一个算法固定、跨平台一致的哈希函数。选 **FNV-1a（64 位）**：实现只有两行、无查表无分支、字节序无关、分布足以支撑特征哈希，是"需要确定性哈希且不想引依赖"时的标准选择。

### 3.2 FNV-1a 原理

FNV = Fowler–Noll–Vo。FNV-1a 64 位的定义为：

```
h = offset_basis                        // 14695981039346656037 = 0xcbf29ce484222325
for each byte b:
    h = (h XOR b) * FNV_prime           // FNV_prime = 1099511628211 = 0x100000001b3
```

对应实现见 `fnv1a`（[Embedder.h](../../src/Semantic/Embedder.h)，源码注释「FNV-1a 64 位」段）：

```cpp
inline uint64_t HashEmbedder::fnv1a(const unsigned char* p, size_t n, uint64_t seed) {
    uint64_t h = seed;                       // 初值即 offset_basis（由调用方传入）
    for (size_t i = 0; i < n; ++i) {
        h ^= static_cast<uint64_t>(p[i]);    // 先异或
        h *= 0x100000001b3ULL;               // 再乘质数
    }
    return h;
}
```

三个设计要点：

1. **`seed` 是初值，不是额外的混淆项**。标准 FNV-1a 用 `offset_basis` 作初值；把它做成参数，意味着可以换一个初值得到"另一个哈希函数"，从而隔离不同向量空间。当前实现固定传 `kFnvOffsetBasis`。
2. **先异或再乘（"a" 的含义）**。FNV-1 是先乘后异或；FNV-1a 调换顺序，使输入字节的最后一位先与哈希低位交互、再被乘法扩散，对短输入的雪崩性更好。
3. **为什么乘的是质数**。乘法是"左移+加法"的混合：它把**低位的信息推进到高位**，同时让整个过程不可逆地搅在一起。选接近 2 的幂的质数，是为了让每次乘法既覆盖全部位、又避免退化成纯移位。质数性保证乘法在 2^64 上可逆（奇数即可逆），因此**不同的输入序列不会被压成同一个中间状态**——碰撞只可能来自最终取模，不会来自迭代过程。

`n == 0`（空串）时循环不执行，返回 `seed` 本身，天然无越界。

### 3.3 分布质量与位白化（`mix`）

§3.1 说选 FNV 是为了确定性与简单，代价是**它的位分布并不均匀**，尤其是**低位**。

原因：乘法中，结果的低位**只由**操作数的低位决定（低位不参与进位传播到低位之外……反向地，乘法结果的高位依赖低位，而低位不依赖高位）。FNV 逐字节异或 + 乘法，低位的"混合深度"有限，呈现可观测的相关性。这是 FNV 的已知弱点。

而本实现取桶用的是 **`h % dim`**。当 `dim` 是 2 的幂（默认 128 = 2⁷）时，取模**等价于取低 7 位**：

```
h % 128  ==  h & 0b1111111
```

也就是说，我们恰好用到了 FNV 最弱的那几位——如果直接取模，不同 n-gram 落入同一桶的概率会**高于**理想均匀分布，把这些无关特征错误地"合并"，制造虚假相似度。

解法是取模前先做一次**位白化**，也就是 `mix`——MurmurHash3 的 64 位终结器 `fmix64`：

```cpp
inline uint64_t HashEmbedder::mix(uint64_t h) {
    h ^= h >> 33;                    // 高位折返到低位
    h *= 0xff51afd7ed558ccdULL;
    h ^= h >> 33;
    h *= 0xc4ceb9fe1a85ec53ULL;
    h ^= h >> 33;
    return h;
}
```

它的目标是**雪崩效应（avalanche）**：输入的任意 1 位翻转，输出约一半的位翻转。三个动作各自的作用：

- `h ^= h >> k`：把高位异或回低位，**让低位获得高位的熵**（这是关键——正是 FNV 低位缺的东西）；
- 两次乘奇数常量：继续扩散，且因为是奇数，**每步都是双射**，不会凭空制造碰撞；
- 收尾再异或一次：保证最高位也被混入。

`mix` 是双射的组合，所以 `mix(h1) == mix(h2) ⟺ h1 == h2`——它只重新排列哈希值，**既改善了分布、又不增加碰撞**。这一步与 §3.8 的"无关文本相似度趋近 0"直接相关。

### 3.4 n-gram：为什么不做整串哈希

如果把**整段文本**直接哈希成一个数，那么"改一个字"会得到完全不同的哈希——两个几乎相同的句子会被判为毫不相干。这在语义缓存里是致命的：我们要的正是"换个说法问同一个问题也能命中"。

所以先把文本切成**互相重叠的**小片段（n-gram，n 为窗口长度），让"部分相同"转化为"部分 n-gram 相同"。

**滑窗方式**：从每个字节偏移起步，取 n 个字节，向后滑 1 字节。长度 `L` 的文本产出 `L - n + 1` 个窗口。

**为什么按字节而不是按字符**：按字节实现只需 `text.data()` + 指针偏移，不需要 UTF-8 解码器，天然语言无关（中英日韩同一套代码）。代价要说清楚：**UTF-8 下"字节窗口"不会对齐到字符边界**——中文每字 3 字节，长度 2 的窗口会切在一个字的内部。这不影响确定性与"相似→共享窗口多"的性质，但对语义的刻画更粗糙。这是本测试替身接受的取舍（真实分词属于 tokenizer 的职责，见 §九）。

**n 的取舍**是一对张力：

| | n 小 | n 大 |
|---|---|---|
| 判别力（区分无关文本） | 弱：短片段易在无关文本中重复出现 | 强：长片段几乎唯一 |
| 抗编辑性（改写后仍相似） | 强 | 弱 |
| 窗口数量 | 多（分母大、噪声小、计算量略大） | 少 |

原因见 §5.1 的实测与推导：**每次编辑会在"仍然相同"的每个连续字节段的两端，各吃掉 `n-1` 个窗口**，所以共享窗口数随 n 增大而减少，而分母几乎不变，余弦相似度随 n 单调下降。

### 3.5 特征哈希（hashing trick）

有了 n-gram 序列，最朴素的做法是建一张**词表**：给每个出现过的 n-gram 分配一个维度下标，向量维数 = 词表大小。问题很明显：维数不固定、随语料增长，且要维护一张全局表（在*测试替身*里尤其不值当）。

**特征哈希**（Weinberger 等，2009）把词表这一步省掉：用哈希函数**直接把 n-gram 映射到固定 `dim` 个桶之一**，模运算就是"取模字典"。

```
bucket(gram) = hash(gram) % dim
```

好处：维数恒定（`dim()` 有确定答案）、无需存储任何表、插入任意新文本都是 O(1)。代价是**碰撞**：不同的 n-gram 可能落到同一桶，被当作同一个特征，给相似度带来噪声。dim 越大碰撞越少（§3.9），但这不是"越大越好"的免费午餐——见 §九。

### 3.6 带符号累加：为什么不能只 `+= 1`

这是本实现里**最容易写错、后果最严重**的一步。

如果每个 n-gram 都往桶里 `+= 1`（只做无符号累加），那么所有向量的分量都 **≥ 0**——整个向量空间被限制在**非负象限**。后果：任意两个非空向量的余弦相似度**恒为正**，而且是可观的数值。两段毫无关系的文本，只要各自有几个 n-gram 撞到同一个桶，就会被算出一个虚假的正相似度；对很短的文本，这个虚假值甚至可能越过 `hitThreshold`，造成**假命中**。

正确做法是给每个 n-gram 一个**随机符号** ξ ∈ {−1, +1}：

```
v[bucket] += ξ(gram)
```

理论依据正是特征哈希的原始论文：使用独立随机符号时，哈希后向量内积是原始（未哈希）内积的**无偏估计**——

```
E[ ⟨φ(x), φ(y) ⟩ ] = ⟨x, y⟩
```

直白地说：**碰撞不再是系统性地"增加"相似度，而是变成一个期望为零的噪声项**。相关文本靠"共享 n-gram"得到正贡献；无关文本的碰撞有正有负、相互抵消，内积趋近 0。§5.1 实测中无关文本得 0.0000、而相关文本得 0.87，靠的就是这一步。

**符号取哪一位**：与桶下标**取不同位**，避免二者相关。

```cpp
const uint64_t h = mix(fnv1a(p + i, window, kFnvOffsetBasis));
const size_t bucket = static_cast<size_t>(h % dim_);   // 低位 → 桶
v[bucket] += (h >> 63) != 0 ? -1.0f : 1.0f;           // 最高位 → 符号
```

经过 §3.3 的 `mix` 白化后，各比特近似独立，因此"低位定桶、最高位定符号"这两件事互不相关。若不做白化而直接从 FNV 的低位取两者，符号会与桶强相关（比如低位为偶的 gram 更可能取到 +1），无偏性就会被破坏。

### 3.7 L2 归一化与余弦相似度

累加完成后，各桶的绝对值大小取决于**撞桶次数**，于是长文本天然拥有更大的向量长度。若直接比较，长度会成为干扰项。因此末尾做 **L2 归一化**：

```
v ← v / ‖v‖ ,   ‖v‖ = sqrt(Σ vᵢ²)
```

归一化后 ‖v‖ = 1，**余弦相似度退化为点积**：

```
cos(a, b) = (a · b) / (‖a‖ ‖b‖) = a · b
```

于是相似度的物理含义变得干净：在带符号累加下，`cos` 近似等于**两个文本共享的 n-gram 占比**（减去无关碰撞的抵消项）。

这与真实模型的口径一致——真实 embedding 通常也做 L2 归一化，[分卷 03 §4.6](../design/03-design-decisions.md) 要求距离/相似度换算只发生在 `VectorIndex` 适配层一次，本条保证了 HashEmbedder 输出的 score 能直接进同一套阈值判定而无需特殊分支（[概念入门 §2、§3](../design/00-primer.md)）。

### 3.8 维度 `dim` 与碰撞

固定桶数 `dim` 控制着"碰撞噪声"：

- **dim 越小**：桶越挤，无关 n-gram 撞在一起的概率越高 → 相似度噪声越大，判别力下降；
- **dim 越大**：碰撞越少，但对测试替身而言只是徒增内存与计算，且对本类的定位没有收益。

`dim = 128` 是"够用且便宜"的折中：一段几十字的提示词横跨几十个 n-gram，128 个桶里的碰撞率足以被 §3.6 的符号机制吸收，同时向量仍然很小。

需要强调：**更大的 dim 不能修复 §5.1 那种因 n 过大导致的相似度下降**——那是共享窗口数变少的问题，与碰撞无关。

## 四、逐段代码解析

代码集中在 [src/Semantic/Embedder.h](../../src/Semantic/Embedder.h)，位于命名空间 `louis::cache`，全部为 header-only（本项目是 INTERFACE 库，见 [src/CMakeLists.txt](../../src/CMakeLists.txt)）。

**1. 接口 `Embedder`**——三个纯虚函数，`modelId` 的注释点明了它的用途（向量空间标识、加载时校验）。

**2. 类声明与方法契约**

```cpp
explicit HashEmbedder(size_t dim = 128, size_t ngram = 2)
    : dim_(dim == 0 ? 1 : dim), ngram_(ngram == 0 ? 1 : ngram) {}
```

- 构造期把 `dim`/`ngram` 夹到 ≥ 1，杜绝后续 `% 0` 与零长度滑窗；
- `dim_`/`ngram_` 是仅有的状态，构造后不再变化；
- `embed` 为 `const`，`dim`/`modelId` 为 `const`——**本类没有任何成员函数会修改状态**，这是线程安全性的来源（§七）。

**3. `kFnvOffsetBasis`**——`static constexpr`，标准 FNV-1a 初值，固定不变才是"可复现"。

**4. `fnv1a` / `mix`**——见 §3.2、§3.3。

**5. `embed`**——三段式：

```cpp
const auto* p = reinterpret_cast<const unsigned char*>(text.data());
const size_t len = text.size();
std::vector<float> v(dim_, 0.0f);

// ① 窗口：不足 ngram 时整串当唯一特征（含空串），保证至少产出一个非零分量
const size_t window = len < ngram_ ? len : ngram_;
const size_t count  = len < ngram_ ? 1   : len - ngram_ + 1;

for (size_t i = 0; i < count; ++i) { /* ② 定桶 + 定符号累加，见 §3.6 */ }

// ③ L2 归一化 + 零向量兜底
float sq = 0.0f;
for (float x : v) sq += x * x;
const float norm = std::sqrt(sq);
if (norm < 1e-6f) { /* 单桶重建，避免 0/0 = NaN */ }
for (float& x : v) x /= norm;
return v;
```

要点：

- **`window` 与 `count` 的取值等价于"滑窗"，但把"长度不足 n"并入了同一条路径**，避免再写一个 if 分支；空串（`len = 0`）时 `window = 0`，`fnv1a(p, 0, basis)` 返回初值，仍会填一个桶 → 空串得到确定的单位向量，而非零向量。
- **零向量兜底**：带符号累加理论上存在"恰好互相抵消为 0"的极端情况（概率极低但非零）。此时 `norm = 0` 会让归一化除零、令相似度变成 `0/0 = NaN`，污染整条链路。兜底逻辑用整串的哈希单桶重建一个合法单位向量，保证 `embed` 的**后置条件恒成立**：输出非零、单位长度、维度为 `dim_`。

**6. `modelId`**

```cpp
return "hash-embedder:v1:fnv1a64:ngram=" + std::to_string(ngram_) + ":dim=" + std::to_string(dim_);
```

把**决定向量空间的所有可变量**编进指纹：算法族（`fnv1a64`）、`ngram`、`dim`。并在注释里定下规则：**任何改变向量空间语义的改动（换算法、换常量、改窗口策略）都必须 bump `v1`**。否则持久化索引会误判新旧空间为同一个，加载后所有相似度都不再有意义（[概念入门 §6](../design/00-primer.md)）。

## 五、参数与实测

### 5.1 默认 `ngram` 为什么是 2 而不是 3

这不是拍脑袋定的，是实测改出来的。用默认 `dim = 128` 测一组中文样本：

| 样本 | ngram=3 | ngram=2 |
|---|---|---|
| 短句，6 字 vs 7 字（差 1 字） | 0.7961（**低于阈值 0.85**） | 0.8652 |
| 长句，21 字 vs 22 字（差 1 字） | 0.9811 | 0.9799 |
| 长句 vs 无关句 | 0.0180 | 0.0000 |

短句在 `n = 3` 时达不到默认阈值，机制可以精确解释。以「今天天气怎么样」（21 字节）vs「今天的天气怎么样」（24 字节）为例：两串**相同的字节区**是前缀 6 字节 + 后缀 15 字节。完全落在这两段内部的窗口数为：

```
前缀：max(0, 6  - n + 1)      后缀：max(0, 15 - n + 1)
n=2 → 5 + 14 = 19        n=3 → 4 + 13 = 17        n=4 → 3 + 12 = 15
```

去重后的实测交集与归一化分母：

| n | 去重 gram 数 A / B | 共享 gram 交集 | 交集 / √(\|A\|·\|B\|) |
|---|---|---|---|
| 2 | 18 / 21 | 17 | **0.8744** |
| 3 | 18 / 21 | 16 | **0.8230** |
| 4 | 18 / 21 | 15 | **0.7715** |

三点结论：

1. **共享窗口数随 n 增大而线性减少**（每个相同字节段两端各被"吃掉" `n-1` 个窗口），而分母 √(|A|·|B|) 几乎不变 → 余弦相似度随 n **单调下降**。预测的 0.8744 / 0.8230 与实测的 0.8652 / 0.7961 吻合（差值是桶碰撞噪声）。
2. 因此 `n = 3` 在短句上会掉到阈值以下；改成 `n = 2` 把短句拉回 0.8652，同时长句几乎不变（0.9811 → 0.9799）。
3. 阈值 0.85 本身是阶段 1 的**占位值**，是"精确率/召回率曲线的操作点"，标定属于阶段 3（[分卷 03 §4.5](../design/03-design-decisions.md)）。所以这里的选择是：让默认参数在**典型短句**上也能通过，而不是反过来让测试样本迁就参数。

### 5.2 默认维度 `dim = 128`

理由见 §3.8。注意它与 `ngram` 一起进入 `modelId`，两者任一改变都会换掉向量空间。

## 六、边界与不变量

| 场景 | 处理 | 保证 |
|---|---|---|
| 空串 `""` | `len = 0` → 单窗口、0 字节 → 返回初值哈希 → 一个桶 | 非零、单位长度，`cos(空,空) = 1` |
| 长度 < `ngram` | 整串作为唯一窗口 | 非零、单位长度 |
| 含多字节中文 | 按字节滑窗 | 确定性；相似文本共享更多窗口 |
| 恰好抵消为 0 | `norm < 1e-6f` 时单桶重建 | 绝不产出零向量，无 `0/0` |
| `dim == 0` / `ngram == 0` | 构造期夹到 1 | 无 `% 0`、无零长窗口 |
| `n == 0` 的 `fnv1a` | 循环不执行 | 返回 `seed`，无越界 |

**类的不变量**（任何输入、任何实例都成立）：

1. `embed(t).size() == dim()`；
2. `‖embed(t)‖ ≈ 1`（浮点误差内）；
3. `embed` 是纯函数：同 `t` 必得逐字节相同的结果，与调用次数、线程、进程无关；
4. `dim()`、`modelId()` 在实例生命周期内恒定。

## 七、确定性、线程安全与性能

- **确定性**：全部随机性都来自"输入内容 → 固定哈希"，实现中没有 `rand`、时间、地址、线程 id 等环境依赖。这是跨进程单测与持久化索引能成立的前提（也是 §3.1 拒绝 `std::hash` 的原因）。
- **线程安全**：`dim_`/`ngram_` 构造后只读，`embed` 不触碰任何共享可变状态、不分配全局资源，因此多个线程并发调用安全。接口把 `embed` 声明为 `const`，正好把这层保证固化下来（[概念入门 §1](../design/00-primer.md) 的向量化调用会被并发高频触发）。
- **性能**：时间 `O(len · ngram)`（窗口数 × 每窗口哈希字节数），空间 `O(dim)`，除返回值外**零额外分配**。对一个只在单测与兜底路径上使用的替身而言绰绰有余。

## 八、`modelId` 指纹与演进规则

`modelId` 是"向量空间身份证"，用途在 [概念入门 §6](../design/00-primer.md) 与阶段 2 的持久化加载校验。规则：

- **进指纹的**：任何改变输出向量语义的东西——算法族、`dim`、`ngram`、以及 `mix`/`fnv1a` 中的常量；
- **当前形式**：`hash-embedder:v1:fnv1a64:ngram=2:dim=128`；
- **变更即 bump**：改动上述任一项，`v1` 必须升版。原因是不升版会让"新旧向量的坐标系不同"被误判为"同一空间"，加载旧索引后算出的相似度全部无意义。

## 九、已知局限与演化路径

**明确不做 / 已知局限**（都是刻意的，属于"测试替身"定位的一部分）：

1. **不代表语义质量**：近义但用词完全不同的句子不会相似——真实 embedding 才具备该能力；
2. **字节级窗口不对齐字符**：中文场景会切在字符内部（§3.4），是"零依赖 + 语言无关"的取舍；
3. **不做任何预处理**：不折叠大小写、不 trim、不分词。这类预处理属于 tokenizer 的职责；
4. **不校准阈值**：只保证序关系成立，`hitThreshold` 的标定是阶段 3 的事。

**替换与拆分触发点**：

- 阶段 2 接入真实模型时，`OnnxEmbedder` / llama.cpp 实现将**另起头文件**，与前文"接口/实现分离"的约定一致；
- 当出现**第二个实现**、或 `fnv1a`/`mix`/归一化这类原语被别处复用（例如将来做"稀疏特征"或"持久化哈希"）时，才把共享原语抽到独立的工具头——**当前不抽**，避免为一个消费者过度抽象。

## 十、如何验证

`HashEmbedder` 的测试点在阶段 1 与编排层解耦，可独立成 `tests/Embedder_test.cc`（`tests/CMakeLists.txt` 用 `file(GLOB *.cc)` 自动收编，无需改构建）：

| 用例 | 断言 |
|---|---|
| `DeterministicSameInput` | 两个实例对同一文本产出逐字节相同的向量 |
| `DimAndUnitNorm` | `size() == dim()`，`‖v‖ ≈ 1` |
| `EmptyAndShortInput` | 空串 / 单字符 / 短于 `ngram` 的串：维度正确、非零、单位长度；`cos(空,空) = 1` |
| `SimilarTextHighSimilarity` | 轻微改写的一对文本 `cos ≥ hitThreshold`，且留安全余量 |
| `UnrelatedTextLowSimilarity` | 无关文本 `cos < hitThreshold` |
| `ModelIdEncodesParams` | 同参相等；`dim` / `ngram` 不同则不同 |
| `ConcurrentEmbed`（可选） | 多线程并发结果一致 |

选样本时避免"只差一个字、恰好卡在阈值附近"的临界用例——阈值标定不是本阶段的目标。

本文 §5.1 的表格即为上述相似度用例的参考数值（默认参数下：短句 ≈ 0.87、长句 ≈ 0.98、无关 ≈ 0.00）。

## 附：术语与参考

- **FNV / FNV-1a**：Fowler–Noll–Vo 哈希族。64 位偏移基数 `0xcbf29ce484222325`，质数 `0x100000001b3`。
- **MurmurHash3 `fmix64`**：MurmurHash3 的 64 位终结器，用于位白化（雪崩）。
- **特征哈希（hashing trick）**：Weinberger, Dasgupta, Langford, Smola, Attenberg, *Feature Hashing for Large Scale Multitask Learning*, ICML 2009。带符号累加使哈希后内积成为原内积的无偏估计，即本实现 §3.6 的依据。
- **UTF-8**：中文常用汉字为 3 字节，是 §3.4 "字节窗口不对齐字符"现象的直接原因。
- 项目内概念对照：[概念入门](../design/00-primer.md)（Embedding / 相似度方向 / 归一化与维度 / 模型生态 / 模型指纹）。
